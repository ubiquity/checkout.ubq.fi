# Checkout decisions

## 2026-10-18: Bun development and Workers Free production

The application uses pinned Bun 1.4.0 for local development, scripts, demo, tests, and dependency installation. Production uses Cloudflare Workers and its `workerd` runtime. This explicitly replaces the former Deno-only project rule; no Deno runtime, CLI, configuration, or deployment requirement remains. Node 24.20.0 is a narrow exception for Cloudflare's supported Wrangler/Miniflare control plane. The Bun test runner builds and launches that control plane when testing real workerd; application execution stays Bun or workerd.

The portable application remains in `main.ts`; `bun.ts` owns the Bun listener and durable local delayed queue, and `worker.ts` owns Worker HTTP, assets, and the exported SQLite-backed Durable Object scheduler. Worker services remain request-local and alarm services are reconstructed per invocation. The Worker import graph contains no Bun-only storage or TLS modules. The owner's final chain-webhook/no-cron decision below supersedes this migration's former no-Durable-Object prohibition and every cron or hosted interval policy, including Bun's optional maintenance interval. Containers, paid relays, and Docker remain outside this deployment.

## Persistence and compatibility

Production continues to use the existing `ubq-kv` Worker service, its D1 database, the `uos_checkout/v1` keyspace, and `CHECKOUT_KV_SERVICE_TOKEN`. No data copy, reset, database replacement, or signing-key rotation is part of this migration. Legacy raw JSON values remain readable. New writes use the versioned `uos_checkout_kv` envelope; every object and array is encoded structurally so arbitrary merchant JSON cannot collide with a nested bigint tag. Public token amounts remain decimal strings.

The shared service implements JSON values, CAS atomics, TTL, and prefix/cursor listing. The adapter treats HTTP 200 atomic conflicts as conflicts instead of transport failures. It fetches all prefix pages, decodes values, then applies typed tuple ordering, start-inclusive/end-exclusive ranges, reverse, and limit. Shared D1 LIKE patterns have a 50-byte bound: oversized derived prefixes fall back only to the wholly Checkout-owned `["uos_checkout", "v1"]` prefix before client filtering. This preserves current service behavior without changing the shared auth backend, at the cost of additional Checkout-only reads as that keyspace grows.

Local state uses Bun SQLite with transaction-backed CAS/versionstamps, snapshot values, expiry-as-absent reads/checks, and the same list semantics. `CHECKOUT_KV_URL` is a local SQLite path; service URL/token settings continue to select the hosted HTTP adapter for Bun.

## Webhook and ingress boundaries

Workers sends the original normalized HTTPS URL using native fetch, fresh application headers, `redirect: "manual"`, a timeout, and no incoming Host, credentials, or Cloudflare destination override. Public DNS prevalidation remains in place. The explicit `global_fetch_strictly_public` and `no_cots_on_external_fetch` compatibility flags enforces the actual connection's public destination after DNS resolution. Worker transport relies on platform TLS verification and does not claim to inspect or pin a peer address. A redirect is a failed delivery and never receives a replay of signed bytes. Response bodies are cancelled without unbounded buffering.

Bun retains hostname-verified TLS plus connected-peer comparison with the approved DNS result set before writing the HTTP request. Real local TLS tests cover trusted certificates, hostname mismatch, and peer mismatch with zero decrypted application bytes on rejection. Tests never disable certificate verification globally.

The Bun listener removes and rebuilds the internal local-peer marker from `server.requestIP()`. Both loopback peer and local HTTP origin are required for the development identity; a production hostname proxied over loopback remains authenticated normally. A Bun process behind the established local reverse proxy reconstructs HTTPS only when the actual peer is loopback, Host is exactly `checkout.ubq.fi`, and `x-forwarded-proto` is exactly `https`; this grants no development identity. The Worker strips the marker unconditionally, including on forged localhost URLs. Checkout retains its existing external Auth Hub origin/issuer pair; this runtime migration does not migrate that external authentication service.

## Maintenance and deployment contract

The owner rule is no cron, ever: no Deno.cron, Worker cron trigger/scheduled handler, setInterval sweep, periodic backstop/retention or timer-driven repair. Chain push remains primary. A new payment attempt, the check-again `{}` claim, a signed chain notification or the payer's four-coordinate report triggers one logical hunt for the authenticated account. No alarm starts an account hunt or drains chain ingress. The account is `(authenticated merchant ID, stored opaque customerReference)` across products and chains; actor IDs, payer/treasury addresses and raw workspace UUIDs do not replace that billing-account reference. Each immutable attempt retains its own product, chain, token, treasury, exact amount and minimum-block snapshot. A new idempotency key creates a distinct attempt; replay returns its original attempt. New attempts have causal account sequence ordering, while equal-createdAt legacy attempts are protected rather than ordered by random ID. UI expiry does not resolve an attempt or remove it as a payment candidate.

Account hunts use only standard JSON-RPC 2.0 array requests, not alchemy_getAssetTransfers or another provider-specific transfer method. Capture latest once per chain, then send disjoint inclusive eth_getLogs chunks of at most 1000 blocks in as few admitted HTTP POST batches as possible; a batch contains unique IDs and no empty array. JSON-RPC cannot reference an earlier entry's result, so an exact newly captured head may need a separate head request. Correlate responses by ID rather than position; retain successful ranges, treat per-entry errors or missing/invalid responses as failures, and reject HTTP errors/non-array replies for the whole sent batch. Retry only failed entries once within the call reserve, and split explicit size rejections within request/response byte and entry bounds. Report exact failed/unsearched ranges and contiguous progress; later successes cannot hide an earlier hole. A latest head below the selected attempts' creation floor is rejected before targetHead is persisted; keep coverage incomplete/head unset so the next related event can recapture. A valid accepted numeric head stays fixed, and minimumBlock minus one remains a legitimate empty span. This adds no polling timer. A conclusively disproved retained inclusion is quarantined by chain, transaction hash, log index and block hash: transfer_review retains its full log, prior ownership/provenance and canonicalContradiction reason while the existing fences atomically persist quarantine and advance the observation cursor. Failed persistence stays pending. Only RpcVerificationError with canonicalContradiction or code non_canonical_block enters this path; missing/null receipt or block data and provider/transport errors remain inconclusive. Quarantine also fails the affected range, clears group/global reachedHead and contiguous progress, and restarts unresolved coverage before deferral. A repeated fork-bearing pass stays incomplete even for an already-quarantined identity. Viable replacement payments can progress, but reservation release requires a new related-event clean range pass and every existing canonical refresh/version/credited-proof/CAS condition. No polling or alarm-driven hunt is introduced. Known P2 recovery limitation ([issue #7](https://github.com/ubiquity/checkout.ubq.fi/issues/7)): after an exact chain/transaction/logIndex/blockHash inclusion is quarantined, repeated fresh hunts skip its canonical re-verification and can remain pending even after RPC recovery. A changed inclusion or a pass without that inclusion can escape; this is not permanent loss of every recovery path. The defect remains in this draft. Reached-head means complete account selection and every required range through captured heads, not a moving head or an unlimited-span guarantee.

The handoff authorizes invalidating earlier unpaid attempts and releasing their active reservations after complete relevant enumeration, successful range coverage, canonical verification and currentness fences. Protect current confirming/payment-bearing attempts. An unchanged return from an inconclusive refresh is not successful verification and cannot authorize release; require fresh canonical safe/finalized evidence with version checks carried into the release CAS. If refresh clears or reverts a payment, invalidate its stale matching assumptions and checkpoint a rematch against current state before any earlier-attempt invalidation. Historical amount ownership is retained permanently after release. If reuse leaves plausible owners in different accounts, persist a manual-review record and automatically credit neither account; an exact existing locator still wins. Incomplete attribution remains unclassified. This conservative shared guard applies to wallet, webhook and hunt paths. This owner-authorized release rule retains a global attribution guard: bare ERC20 transfer data does not identify a future payer's original dialog intent.

Expiry remains ONE finite per-invoice backup pass to its captured latest head, independent progress, bounded chunks, consecutive-failure cap and first-execution window. Its completion/partial marker ends only that pass: it does not invalidate an unresolved attempt, release its amount or authorize an alarm-driven account hunt. Late UI-expired attempts remain eligible until actual credited/invalidated resolution. The accepted runtime preserves this expiry boundary and adopts legacy account indexes; no old scheduler-complete marker is proof that every legacy attempt/history descriptor is indexed.

The provider-neutral chain-event processor is exposed through the Alchemy adapter at `POST /api/v1/chain-events/alchemy`. `CHECKOUT_ALCHEMY_WEBHOOK_KEYS` is a secret JSON map `webhookId -> {network, signingKey}`; each subscription is pinned to its network and unique literal UTF-8 signing-key bytes. The adapter accepts token/erc20 activity labels and one-to-nine-digit UTC timestamp fractions while retaining strict ERC20 log validation. Verify HMAC-SHA256 over the unchanged raw body against the hex X-Alchemy-Signature before receipt/domain access. Reject missing/invalid signatures, unsupported subscriptions/networks, malformed payloads, and stale/future payloads. The 256-KiB body and 256-activity admission caps are application limits, not documented Alchemy maxima. The createdAt window is at most 15 minutes old and 60 seconds future as application policy; official docs/source do not establish notification-time semantics, so compatibility with an old registered webhook requires owner live verification before claiming production acceptance.

Each transfer uses its own transaction hash, log index, block number/hash, token, recipient and integer amount. A hunt enumerates every unresolved attempt in the account through bounded account-index pages, groups historical token/treasury snapshots per chain, and searches from each group's earliest unresolved block to one captured numeric latest head. It matches against all eligible attempts in that group at once. Exact transaction-locator ownership takes precedence over reservation reuse; other accounts' payments remain isolated. Canonical receipt/block verification, not a log or signature alone, establishes confirming payment state and reorg transitions. Relevant transfers without a uniquely attributable live attempt are durably retained for review rather than silently discarded. An identical current inclusion is idempotent, but an additional distinct transfer to an already-paid attempt must enter the duplicate/manual-review retention path rather than terminal ignored. Incomplete ownership reads stay unclassified, not credited or treated as another account's money.

`POST /api/v1/invoices/{id}/claims` accepts exactly `{}` or the existing four-coordinate body. The stored anchor invoice supplies the authenticated account; an account hunt must still return that requested invoice ID and keep discovery.found consistent with its current payment, even when a peer attempt is paid. Preserve `{ invoice, eventJws?, discovery?: { found, searchedToBlock? } }` and decimal-string progress. Reuse a signed event only when its anchor version, payment and lifecycle state still match the returned invoice. Otherwise admit the complete event/index/signing-key lookup cost with cleanup headroom; omit optional eventJws when capacity is insufficient instead of turning a completed hunt into a budget failure. Add account coverage and per-attempt credited/confirming/nothing-yet/invalidated outcomes only through the agreed additive response contract, without adding incompatible invoice.status values. The current Prospector parser drops additive fields and its HTTP/browser projections require a consumer update before those outcomes can be claimed visible. The accepted runtime fields are recorded below; consumer UI visibility and production acceptance remain separate. Parser acceptance alone is not UI acceptance.

The accepted runtime adds accountHunt with complete, reachedHead, pending and diagnostics; attempts entries contain invoiceId, outcome (credited, confirming, nothing_yet or invalidated) and searchComplete; groups contain chainId, tokenAddress, treasuryAddress, optional decimal-string targetHead/searchedToBlock and reachedHead. Complete means this pass's covered observations/refresh/resolution work finished, not that every attempt was paid or invalidated. ReachedHead describes captured-range coverage, not canonical credit. Legacy discovery.searchedToBlock maps the anchor's chain/token/treasury group. Legacy found:false or nothing_yet is allowed with incomplete work; failed ranges cannot prove an attempt unpaid or authorize invalidation, and pending/coverage diagnostics must expose the gap. A canonical payment is recorded at latest as confirming immediately; three sealed blocks do not grant credit or emit an early credit-bearing accepted event. Actual safe or finalized head evidence permits the accepted/settled lifecycle and credit. Existing public phase names remain compatible; legacy provisionally_paid records retain their historical classification. Known payments schedule only finite safe/finalized milestones keyed to the inclusion/generation: Ethereum +768/+1152 seconds, Optimism +300/+1800 seconds and Base +120/+1200 seconds from the canonical payment timestamp. These are local timing estimates, not proof or deadlines. A final late/null head leaves pending state until a related authenticated request, write or chain event; no periodic head recheck or new-payment search is introduced.

Shared KV remains authoritative for invoices, payment/event records and discovery/receipt progress. Worker scheduling crosses two stores with a prepared intent: durably arm every target before the fenced domain/committed-intent CAS; cancel an uncommitted preparation by versionstamp CAS before dropping it, and retire a committed intent only after every target durably adopts. Replay preserves newer generations, earlier deadlines, progress, attempts and delivered state. Every continuation checks its durable operation/generation or lease after external awaits and before further I/O, completion or alarm changes; stale work cannot release a successor or overwrite a newer inclusion. No credential is stored in job, receipt, intent or DO storage.

Bun shares the pure job core with the DO adapter and uses the approved durable local KV delayed queue. The job and due-index entry commit atomically with the originating domain change. Each process startup hydrates committed jobs and makes one finite idempotent existing-domain adoption pass, preserving valid generations, leases, deadlines and expiry progress. This is per startup, not a permanent migration-complete marker. Enqueue/dequeue/delivery/startup and related request/write events refresh the queue head. One one-shot callback delivers the next known job at its due time, chaining that job's long delay if needed. It is neither a sweep nor timer-based recovery. After independent startup hydration, Bun request recovery follows authenticated, scoped, invoice-owned domain events; pathname or HTTP success alone does not authorize queue refresh/rearm. Invalid webhooks cause no post-startup KV/queue recovery. Rejected merchant requests may perform necessary authentication-record lookups, but must not recover queued work. An exact attributed signed notice for an unchanged current inclusion can call existing wakeups.ensure after token, treasury, amount, minimum block, invoice/payment attribution and a receipt-currentness fence, with another currentness check before terminal acknowledgment. The retained due entry/generation stays stable. Require 11 available slots for pre-check, ensure/bounded adoption and post-check; insufficient capacity or stale currentness defers, and unavailable ensure leaves the receipt pending/HTTP503 for identical signed-notice retry. Unrelated notices and duplicate locators cannot recover other queued work. A lost in-memory callback is recovered only by startup, a related request/write, or the work's originally registered alarm.

The runtime uses migration:checkout-events-v2 with checkout_migration_v2 phases invoices, accounts, outbox and complete. The accounts phase advances shared [uos_checkout,v1,payments,account_index_v1] state (complete/cursor/retained page IDs/next/offset). Account and ownership manifests use exact 64-entry account_pages/ownership_pages keys with account_membership revision/sequence/count and ownership_membership count controls; attempt_states stores internal resolution separately from invoice.status. Missing/inconsistent manifests are not complete coverage. Legacy adoption writes permanent ownership and treasury_history descriptors for all valid invoice snapshots, including invalidated/history addresses needed for late-transfer review. Bun performs one finite legacy adoption pass per process startup; Worker v2 completion must include the accounts phase, not reuse v1 as proof.

The first ordinary Worker request starts a one-time migration through bounded request slices, not a migration alarm. Persist phase, raw prefix/cursor, bounded page identities/next cursor and item offset; checkpoint only durable adoption and never advance past unarmed work. While migration is pending, ordinary application requests return HTTP 503 migration_pending before entering their handler; GET /api/health remains 200 and advances a bounded slice. The owner issues a finite GET health cutover batch until x-checkout-events-migration is complete. Even the slice writing the completion marker reports pending; the next entry-complete request reports complete with zero shared-KV migration work. HEAD is not the migration health path, and HTTP 200 alone does not prove completion. Use a bounded raw service-page API within the Checkout keyspace, not list(limit) that collects every page first. Adopt all legacy account-attempt references and permanent ownership descriptors, including UI-expired unresolved candidates, plus separate expiry jobs, finite safe/finalized jobs and undelivered outbox work including future retries; never synthesize payment polling or expired/reverted watchers. Completion must cover the current account-index/history schema; a previous scheduler-only complete marker is insufficient. The accepted versioned schema is recorded below. Completion stays quiescent. Verify chain webhook authentication before any KV-backed migration/recovery, so malformed or invalid-HMAC deliveries cause no storage work. Settle old unfenced writers before accepting coverage; if one could have written behind the cursor, trigger a fresh versioned migration event. Each Bun process startup hydrates committed queue jobs and runs one finite existing-domain adoption pass, even when a previous process completed its pass; valid existing jobs remain intact. This permits shared-KV reuse after Worker-created work without a permanent local completion marker or periodic scan.

Merchant event creation schedules one delivery job; failed attempts retain authoritative nextAttemptAt and backoff, delivered events cancel work, and renewed signatures retain event JTI. Durable attempt ownership suppresses concurrent duplicate wakes, but HTTP success can occur before its acknowledgment is recorded, so delivery after ambiguous outcomes is at least once and requires recipient deduplication; no physical exactly-once claim is made. Existing codec, legacy reads, shared keyspace/KV token, signing identity, admin/merchant authentication, public-egress transport and ingress trust remain in force. The inbound Alchemy secret is owner-provisioned setup, not an agent-created credential. Existing invoice/payment/event history and permanent amount-ownership descriptors are retained. Invalidated active reservations follow the complete-coverage release rule above; no history purge or periodic retention job is introduced. Terminal invoice statuses alone do not prove global quiescence. A budgeted request can leave an unadopted COMMITTED wake intent for that target. Only the target's related request or its already registered original alarm advances bounded adoption/ACK/retirement; unrelated requests do not sweep other entities. Quiet is asserted after all legitimate jobs and per-target committed intents are adopted/retired, without a new cleanup timer or history deletion.

Platform facts checked on 2026-10-18: Workers Free HTTP CPU is 10 ms, external subrequests are 50/invocation, service bindings have a 32-Worker-invocation ceiling, and account requests are 100,000/day. The DO-specific default is 30 seconds CPU, with 15-minute alarm wall time. Free SQLite DO allowances are 100,000 requests/day including alarms/RPC sessions, 13,000 GB-s/day, 5 million row reads/day, 100,000 row writes/day and 5 GB account storage; setAlarm writes one row. Preserve conservative budgets and completion headroom without a paid CPU override. Runtime limits are Worker HTTP 30 charged slots, entity alarm 28, migration ensure 24 and nested adopt 7. Nested allowances are reserved INSIDE the caller envelope with completion capacity protected, not added after 30. The native manual HTTP ledger used 28 actual root calls (23 storage, 3 RPC, 2 bindings), leaving 2 slots. A separate HTTP row used 21 actual root calls plus a reserved 7-call nested upper bound, leaving 2; adding the entry yields a conservative bound of 29. Seven is a reservation, not observed nested traffic. The harness bounds actual calls plus reserved nested plus entry at32 and actual calls at50 across recorded contexts; printed detailed rows are HTTP only. Do not sum independent alarms or claim exact nested attribution beyond these bounds. Live CPU/quota capacity remains unproved. Daily exhaustion rejects affected operations until 00:00 UTC; docs do not promise automatic overdue catch-up. Alchemy lists five Free webhooks and up to ten-minute Free/PAYG retry backoff for non-200 responses. Three required mainnet subscriptions fit only if account capacity is available. Admission caps, finite provider retries, partial expiry coverage and finite confirmation checks do not guarantee unattended completion; retained work may await a permitted related event, never polling.

Automatic push/PR quality checks are offline; networked Anvil remains an explicitly selected optional command. `bun run check` covers Prettier, ESLint, both Bun and Worker TypeScript entry points, the isolated offline suite, real Bun ingress/TLS checks, and the real workerd harness with mocked storage/RPC/DNS/webhook upstreams. The harness does not write production state. `bun run test:anvil` is a separate networked demo acceptance requiring Foundry and pinned Base fork access. `bun run deploy:dry-run` verifies Worker packaging. Production readiness additionally requires the deployed public path, retained JWKS identity, authenticated API behavior, owner-configured chain delivery, and actual alarm/migration acceptance; build and mock evidence do not establish them.

The `candidate` environment has no routes or cron and needs its own non-inherited SQLite DO binding. Production targets only `checkout.ubq.fi/*` and the established `ubq-kv` service. CI deploys the `development` branch using the existing protected `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` credentials; the Checkout KV token and owner-provisioned Alchemy key map stay Worker secrets. Both production and candidate require the Alchemy secret, so the owner installs its map on the existing Worker before deploying this reviewed code; then a finite GET health migration must report entry-time complete before notification activation/cutover. Cutover must settle old unfenced/interval writers and verify event-triggered migration and owner-configured chain delivery. Retain a Bun release with the current codec as the reversible target until acceptance passes; no rollback may restore cron or a maintenance interval. The old adapter cannot read newly enveloped values and must not be restored after new writes.
