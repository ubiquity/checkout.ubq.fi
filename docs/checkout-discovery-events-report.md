## Selected behavior and accepted foundations

Each payment-dialog invoice is an attempt with a distinct reserved amount; intentional creation is separate from an idempotent replay. The account is `(authenticated merchant ID, stored opaque customerReference)`, grouping unresolved attempts across products/chains while preserving immutable product/token/treasury/minimum-block snapshots. One-hour UI expiry does not resolve candidacy. Check-again `{}`, wallet coordinates, signed chain notification and new-attempt creation are event triggers for one logical account hunt through captured latest heads, not one 1000-block search per press. A new idempotency key creates a distinct attempt; replay keeps the original. New equal-time attempts have causal sequence ordering, while legacy createdAt ties remain protected.

The standard JSON-RPC 2.0 log array carries disjoint <=1000-block requests with unique IDs, correlates unordered results by ID, retains success, retries failed/missing/invalid entries once within the reserve and splits explicit size rejection within byte/entry/call bounds. An exact newly captured numeric head can require its own POST because batch entries cannot reference one another's results. HTTP/non-array failure fails the sent batch; never send an empty batch. Incomplete enumeration, exact failed/unsearched ranges and contiguous searchedToBlock remain explicit. A bounded implementation does not promise arbitrary-span completion or hide failed holes.

Canonical latest observations record confirming immediately. Actual safe/finalized evidence permits credit-bearing events; three sealed blocks grant no credit. Existing merchant/event identity, canonical reorg and idempotent fulfillment paths remain. The invoice-ID response keeps the requested anchor invoice and its actual discovery.found value with the legacy invoice/eventJws/discovery shape. Account coverage and per-attempt credited/confirming/nothing-yet/invalidated outcomes are additive, not new incompatible invoice.status strings. Current Prospector parsing drops additive data and its HTTP/browser projections require consumer integration before those outcomes are claimed visible; accepted fields and evidence are recorded below; current consumer projections still require separate integration for visibility.

Earlier unpaid attempts can be invalidated and active reservations released only with complete relevant enumeration/ranges, successful fresh canonical verification and currentness fences; an inconclusive refresh is not proof, and a payment-clearing refresh requires rematching before release; current confirming/payment-bearing attempts are protected. Permanent amount-ownership history remains after release. Ambiguous reuse across accounts is retained for manual review with no automatic credit to either account, while an exact existing transaction locator wins. Incomplete ownership reads stay unclassified. Relevant unmatched transfers are retained for review rather than silently discarded. A distinct additional transfer to an already-paid attempt must also reach duplicate/manual-review retention; identical current-inclusion replay remains idempotent. This is the handoff-authorized release policy with a conservative global attribution guard, not an unanswered preference being treated as approval.
