## Account attempts and check-again

Each intentional payment-dialog creation is an attempt with its own reserved amount; replay of the same idempotency key is not a new attempt. The account is authenticated merchant plus the stored opaque customerReference, including the persisted billing-account reference used for workspace purchases. New-attempt creation, check-again `{}`, wallet coordinates and signed chain notifications trigger one logical hunt of all unresolved account attempts across their historical chains/token/treasury groups. UI expiry does not end candidacy. Hunt chunks are standard eth_getLogs requests in JSON-RPC 2.0 array batches through captured latest heads; returned error/coverage gaps are explicit, with selective failed-entry retry and bounded size splitting rather than a 1000-block-per-press promise.

A latest canonical observation is confirming, not credited. Actual safe/finalized evidence permits credit-bearing events. Complete relevant enumeration/ranges, canonical checks and currentness fences are required before earlier unpaid attempts are invalidated and their active reservations released; current confirming/payment-bearing attempts are protected. Historical amount ownership remains permanent. Ambiguous cross-account reuse is retained for manual review with no automatic credit to either account; exact locator ownership still wins, and incomplete ownership reads remain unclassified. Relevant unmatched observations are retained, not silently discarded.

The invoice-ID claim still returns its requested anchor invoice and its actual discovery.found state. The accepted runtime adds accountHunt with complete, reachedHead, pending and diagnostics; attempts entries contain invoiceId, outcome (credited, confirming, nothing_yet or invalidated) and searchComplete; groups contain chainId, tokenAddress, treasuryAddress, optional decimal-string targetHead/searchedToBlock and reachedHead. Complete means this pass's covered observations/refresh/resolution work finished, not that every attempt was paid or invalidated. ReachedHead describes captured-range coverage, not canonical credit. Legacy discovery.searchedToBlock maps the anchor's chain/token/treasury group. Legacy found:false or nothing_yet is allowed with incomplete work; failed ranges cannot prove an attempt unpaid or authorize invalidation, and pending/coverage diagnostics must expose the gap. ## Finite cutover and local startup

The first ordinary Worker request starts bounded migration slices; migration has no alarm of its own. While pending, ordinary application requests return HTTP 503 with error migration_pending before their handler; GET /api/health remains HTTP 200 and advances a bounded slice. Use GET, not HEAD. Inspect x-checkout-events-migration and issue only a finite owner-controlled batch of these health requests until it reports complete BEFORE activation/cutover. The slice that writes the complete marker still reports pending; issue the next GET, which observes entry-time complete with zero shared-KV migration work. HTTP 200 alone, a missing header, or the final pending slice is not completion. If the finite batch ends pending, stop and report retained progress instead of installing a timer.

```bash
curl --request GET --silent --show-error --dump-header - --output /dev/null https://checkout.ubq.fi/api/health
```

Migration persists bounded phase/raw-page/item progress and adopts all required legacy account-attempt references and ownership history, including UI-expired unresolved candidates, alongside separate expiry, safe/finalized and merchant-delivery jobs. The runtime uses migration:checkout-events-v2 with checkout_migration_v2 phases invoices, accounts, outbox and complete. The accounts phase advances shared [uos_checkout,v1,payments,account_index_v1] state (complete/cursor/retained page IDs/next/offset). Account and ownership manifests use exact 64-entry account_pages/ownership_pages keys with account_membership revision/sequence/count and ownership_membership count controls; attempt_states stores internal resolution separately from invoice.status. Missing/inconsistent manifests are not complete coverage. Legacy adoption writes permanent ownership and treasury_history descriptors for all valid invoice snapshots, including invalidated/history addresses needed for late-transfer review. Bun performs one finite legacy adoption pass per process startup; Worker v2 completion must include the accounts phase, not reuse v1 as proof. It never creates discovery jobs. Invalid chain deliveries are rejected before KV-backed migration/recovery. If a chosen finite request batch still reports pending, report retained progress and continue through an authorized ordinary-request event; do not install a sweeper. Settle old unfenced writers before claiming complete coverage. Each Bun process startup hydrates its durable queue and runs one finite idempotent existing-domain adoption pass, preserving valid jobs and adopting required legacy attempt/history state rather than trusting a permanent local completion marker; thereafter one-shot callbacks deliver recorded due jobs, with head refresh only on enqueue/dequeue/delivery/startup or related requests/writes.

Known-payment local safe/finalized estimates from the canonical timestamp are Ethereum +768/+1152 seconds, Optimism +300/+1800 seconds and Base +120/+1200 seconds. They are scheduling estimates, not phase proof or deadlines. Three sealed blocks grant no credit. Actual canonical receipt/block and safe/finalized heads govern phases; a final late/null observation remains pending until a related event, without recurring head polling. Terminal invoice statuses alone do not prove global quiescence. A budgeted request can leave an unadopted COMMITTED wake intent for that target. Only the target's related request or its already registered original alarm advances bounded adoption/ACK/retirement; unrelated requests do not sweep other entities. Quiet is asserted after all legitimate jobs and per-target committed intents are adopted/retired, without a new cleanup timer or history deletion. [Ethereum timing](https://ethereum.org/developers/docs/consensus-mechanisms/pos/), [Optimism finality](https://docs.optimism.io/op-stack/transactions/transaction-finality.md), and [Base finality](https://docs.base.org/specifications/transactions/transaction-finality.md) explain the approximation.

The adapter accepts token or erc20 activity labels with the same strict ERC20 log checks, and UTC createdAt strings with one through nine fractional digits. Nanosecond-formatted provider timestamps are accepted syntactically; timestamp freshness semantics still require the owner live check above.
